# Spike 2.4 — 전 모델 상주 OOM 실측 (게이트)

작성: 2026-07-30 · 관련 Task: Plans.md 2.4 · 상태: cc:완료

## 목표

PRD "OOM 전략"의 주력안(전 모델 상주, 언로드 회피)이 GB10(119GB unified memory)
에서 실제로 버티는지 실측. Depends 2.1·2.2·2.3·2.3.5 — 이 시점에 확정된
씬분할(Nemotron-3-Nano-4B-GGUF)·비전캡션(gemma4)·T2I(FLUX.1-schnell) 3개만
대상. I2V(LTX/Cosmos/Wan)·TTS는 아직 미확정이라 이번 실측 범위 밖(별도
재실측 예정).

## 사전 이슈: ollama 동시 상주 제약

시스템 전역 ollama systemd 서비스가 `OLLAMA_MAX_LOADED_MODELS=1`로 설정돼
있어 씬분할+캡션 두 ollama 모델이 애초에 동시 상주 불가(둘 다 ollama 서빙).
`/etc/systemd/system/ollama.service.d/override.conf`에
`OLLAMA_MAX_LOADED_MODELS=2` 추가(사용자 승인, sudo로 직접 적용) 후 실측
진행. **이 override는 테스트용으로 남겨둔 상태** — 원복 여부는 별도 결정
필요.

## 방법

1. baseline: 테스트 시작 전 이미 상주 중이던 GPU 프로세스 3개 확인
   (`nvidia-smi --query-compute-apps`) — video_generator·ComfyUI와 무관한
   `daol_fascope.wafer_predict_server`(14.3GB) 포함 총 36.4GB, 시스템 메모리
   `free -h` 기준 64Gi 사용 중.
2. ollama에 Nemotron-3-Nano-4B-GGUF + gemma4:latest를 `keep_alive:-1`로
   순차 로드 → 82Gi 사용(+18Gi).
3. `video_generator/hunyuan_server/bench_t2i.py flux-schnell`을 백그라운드
   실행하며 5초 간격으로 `free -h` 폴링.

| 타임아웃 후 재확인 | 48Gi — `818144`(video_generator server.py, GPU
  21.9GB 보유자) 프로세스가 사라짐. 로그 파일 없어 OOM-kill 확정 불가하나

산수: baseline 36.4GB + Nemotron 8.2GB(nvidia-smi 실측) + gemma4 7.3GB +
FLUX 단독 peak 33.8GB(2.3.5 실측치) ≈ 85.7GB인데 실측은 118GB까지 상승 —
약 32GB 오버헤드. 원인 후보: ollama 두 모델 모두 기본 최대 컨텍스트
(131072 / 262144 토큰)로 로드되어 KV캐시가 필요 이상 크게 잡힘,
diffusers `.to("cuda")` 전환 중 CPU/GPU 이중 보유(2.3.5 Qwen-Image-Flash와
동일 패턴).

## 결론

**전 모델 상주(PRD 주력안) 채택 안 함 — 폴백(배치 온디맨드 언로드) 채택.**

I2V/TTS를 더하기 전, 확정된 3개 모델만으로도 baseline 상주 서비스와 합쳐
119GB를 넘겨 실제 프로세스 크래시까지 발생했다. 상주 전략을 강행할 여지가
없다고 판단.

- **채택 정책**: 배치 온디맨드 언로드. 파이프라인 진입 시 필요한 모델만
  로드 → 배치 완료 후 언로드, 씬별 왕복 로드는 하지 않음(PRD 폴백 조항
  그대로).
- **재실측 예정**: I2V(LTX distilled+Face-ID / Cosmos-Predict2-2B / Wan
  폴백)·TTS 모델이 확정된 뒤, 확정 스택 전체로 상주 가능 여부를 한 번 더
  실측한다(이번 3-모델 실측 결과가 최종 판단은 아님 — 조합이 달라지면
  재검토 여지 있음, 특히 daol-fascope 등 무관 서비스가 상시 점유하는
  14.3GB가 이 머신 예산에서 큰 비중이라는 점도 고려).
- `OLLAMA_MAX_LOADED_MODELS=2` override는 다음 재실측 때도 필요하므로 일단
  유지.
