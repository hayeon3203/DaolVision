# Spike 3.6 — ComfyUI 모델 로딩 스파이크 완화 플래그 조사

작성: 2026-07-31 · 관련 Task: Plans.md 3.6 · 상태: cc:완료(조사 완료, 채택 없음)

## 배경

3.3(`docs/spikes/3.3-ltx-bottleneck-profile.md`) 1차 시도에서 ComfyUI GGUF 로드
중 별도 프로세스(`flux_server.py`)가 동시에 대형 모델을 로드하면서 시스템
가용메모리가 1.7GiB까지 떨어져 24분+ 사실상 정지(스왑 스래싱)한 사례가
있었다. `.harness/STATE.md`는 이를 UVM(CUDA 통합메모리) 스톨로 재확인하고
"GPU-매핑 페이지가 회수 후보로 안 잡히게 여유 유지"를 목표로 남겼다(4.4/3.6
근거). 이 태스크는 그 완화책이 ComfyUI CLI 플래그로 가능한지 조사한다.

## 조사한 플래그 (`comfy/cli_args.py`)

| 플래그 | 의미 | 이번 문제와의 관련성 |
|---|---|---|
| `--cache-ram [active] [inactive]` | RAM 압박 기반 캐시 자동 축출(기본값) | 헤드룸 확보에 가장 직접적으로 부합 |
| `--cache-classic` | 구형 무조건 캐시(현재 `comfyui.service` 설정값) | RAM 압박과 무관하게 캐시 유지 → 헤드룸 잠식 후보 |
| `--vram-headroom N` / `--reserve-vram N` | 항상 N GB를 비워두도록 강제 | STATE.md가 명시한 "여유 유지" 목표와 정확히 일치 |
| `--highvram` (현재 사용중) | 사용 후에도 모델을 GPU 상주 유지 | 반복 실행 재로드 방지(속도용, `comfyui_workflows/README.md`가 근거) — 끄면 프롬프트마다 +50~80초 |
| `--disable-mmap` | safetensors mmap 비활성화 | 기본이 mmap 사용(안전)이므로 끄면 오히려 로드 시 전체를 RAM에 복사해 스파이크 악화 — 채택 대상 아님, 참고용 |

가장 유력한 단일 변수 후보로 `--cache-classic` 제거(기본값 `--cache-ram`
복귀)를 선정 — 노드 출력 캐시가 RAM 압박 시 자동 축출되어 다음 모델 로드
시점에 헤드룸을 돌려준다는 가설이 STATE.md 목표와 가장 직접적으로 맞아떨어짐.
`--highvram`은 README에 문서화된 반복실행 속도 근거가 있어 조사 대상에서
제외(끄지 않음).

## 방법 (적용 전/후 재측정)

현재 production 채택 모델(3.8, LTX-13B-distilled fp8, 단발샷 I2V, ~30초/8-step
— 3.3의 LTX-2.3-22B GGUF Face-ID 523초 파이프라인은 폐기 트랙이라 대상에서
제외)로 `probe_ltx13b_i2v.py`를 각 조건마다 `comfyui.service` 재시작(캐시
완전 클리어) 직후 1회 실행, 0.5초 간격 `free -m` 폴링으로 가용메모리/스왑
최저치를 기록.

- **전 (`--cache-classic --highvram`, 기존)**: 04:52:29 제출, 로드 78.3초
  (checkpoint 역직렬화+text encoder+VAE), 샘플링 20초, 총 105.50초.
  `min_available=51576MB`, `max_used=70926MB`, `max_swap=10453MB`.
- **후 (`--highvram`만, `--cache-ram` 기본값)**: 04:55:35 제출, 총
  102.60초. `min_available=51444MB`, `max_used=71057MB`, `max_swap=10452MB`.

## 결론

**측정 가능한 차이 없음** (가용메모리 ±130MB, 스왑 변화 없음, 소요시간 차이
~3초는 실행 간 노이즈 범위) — `--cache-classic` 제거로 인한 이득 없음,
production 플래그(`--cache-classic --highvram`) 원복 완료.

이유: 이번 단발샷 워크플로는 실행마다 입력(참조 이미지·프롬프트)이 달라
캐시 히트가 원천적으로 없다 — 노드 출력 캐시 정책(classic vs ram-pressure)이
차이를 낼 여지 자체가 없는 그래프 구조. 그리고 3.3에서 관측된 진짜 위험한
스파이크(가용메모리 1.7GiB, 24분+ 정지)는 **ComfyUI 자체의 로딩이 아니라
별도 프로세스(`flux_server.py`)와의 동시 대형 모델 로드 경합**이 원인이었다
— ComfyUI 프로세스 내부 CLI 플래그로는 다른 프로세스의 메모리 점유를 제어할
수 없다. 이번 단독 실행 조건에서는 애초에 최저 가용메모리가 51GiB로 넉넉해
위험 상황 자체가 재현되지 않았다(정상 조건에선 문제 없음을 재확인).

**진짜 완화책은 Task 4.4(OOM 오케스트레이터)의 몫**: 동시 대형 모델 로드를
프로세스 간에 직렬화/차단하는 것이지, 개별 서비스의 캐시 플래그가 아니다.

## 산출물

- 이번 조사는 재현 스크립트를 남기지 않음(1회성 `free -m` 폴링 bash 루프,
  기존 `probe_ltx13b_i2v.py` 그대로 재사용) — 필요시 3.3의
  `tests/probe_ltx13b_i2v.py`를 동일 방식(서비스 재시작 후 실행 + `free -m`
  폴링)으로 재현 가능.
- `comfyui.service`는 원래 설정(`--cache-classic --highvram`)으로 원복 완료.
