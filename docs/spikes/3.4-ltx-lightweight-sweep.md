# Spike 3.4 — LTX I2V 경량화 파라미터 스윕

작성: 2026-07-31 · 관련 Task: Plans.md 3.4 · 상태: cc:완료

## 목표

3.3 baseline(8-step/Q6_K/Face-ID strength 1.0, 523.44초) 대비 더 가벼운 조합이
있는지 스윕. 조합별 생성시간 실측 + 얼굴/화풍 유지 눈판정, 최소 4~5초 분량
유지가 DoD.

## 방법 · 도구

3.3의 `probe_ltx_profile.py`를 재사용, `sys.argv[1]`로 노드별 override JSON을
주입할 수 있게 확장(예: `{"99": {"strength_model": 0.75}}`). 매 조합 제출 전
`comfyui.service`를 재시작해 ComfyUI 노드 캐시가 이전 실행 결과를 재사용해
"0.01초 실행"으로 위장하는 걸 방지(최초 발견: 시드+강도 조합이 처음이었는데도
전체 노드가 `execution_cached`로 잡혀 새 영상이 안 나온 사례 있었음).

## 세부 발견

### 1. step 6 — 명확히 기각

`ManualSigmas`(node 68)가 실제 스텝 소스(`BasicScheduler`/node 66의 `steps`
위젯은 dead branch, `SamplerCustomAdvanced`가 66이 아니라 68을 참조). 8→6
step은 임의로 자르는 게 아니라 원래 9포인트 시그마 스케줄을 곡선 형태 유지하며
7포인트로 리샘플해서 테스트(`numpy.interp`). 결과: 배경 디테일은 유지되나
Face-ID 컨디셔닝이 latent를 하나의 identity로 수렴시킬 시간이 부족해 **주인공
옆에 거의 동일한 옷차림의 두 번째 인물이 프레임 내내 붙어있는 twin 아티팩트**
발생(8-step baseline에도 배경에 작은 엑스트라가 있으나 원거리·소규모라 이와
질적으로 다름). 저스텝 diffusion의 전형적 결함으로 판단, 기각.

### 2. Face-ID strength 0.75 — 시드 고정으로도 검증 실패

처음엔 무작위 시드라 강도 효과와 구도 변화가 섞여 판단 불가 → baseline과
동일 시드(`1035625245488400`)로 고정 재실행. 그런데 **시드를 정확히 고정해도
카메라 구도가 baseline과 다르게 나옴**(`/history`로 제출된 프롬프트의 seed
값이 의도대로 반영됐음을 직접 확인했음에도). GPU 병렬 연산(attention/matmul)의
부동소수점 비결정성이 8-step 누적 과정에서 구도 차이로 증폭된 것으로 추정 —
이 파이프라인에서 시드 고정만으로 완전한 재현성을 보장할 수 없다는 뜻. 강도
효과가 속도에 영향 없다는 것만 확인, 정합성 판정은 데이터 부족으로 미결.

### 3. GGUF Q5_K_M — 트레이드오프, 속도 이득은 노이즈에 묻힘

가중치 로드 크기는 15.6GB(Q6_K 17.2GB 대비 확실히 작음)로 예상대로. 그러나
스텝당 시간이 1차 20.28초/it, 2차 28.27초/it로 46% 편차 — 아래 "UVM 스톨"
문제로 이 세션 컨디션 자체가 매번 크게 흔들려서 "Q5_K_M이 더 빠르다"고 결론
내릴 수 없음. 얼굴 정합성은 육안으로 명확히 한 단계 하락(턱선·헤어 파팅
불일치) — 구조적 파탄(twin 등)은 없어 6-step보다는 낫지만, 속도 이득이
불확실한 채로 품질만 떨어뜨리는 조합이라 미채택.

### 4. 세션 전반 — UVM(통합메모리) 스톨, 반복 재현됨 [4.4/3.6에 근거로 남김]

GB10은 CPU/GPU가 NVLink-C2C로 물리 메모리 풀 하나를 공유(`system_stats`의
`ram_total`==`vram_total`, 122503MB로 완전 동일). PyTorch가 `cudaMallocAsync`
(managed/unified memory 계열)를 씀. 시스템 메모리가 1~2GB대로 빠듯해질
때마다(다른 GPU 서비스 상주 + 이번 로드가 겹칠 때) **GPU가 매핑 중인 페이지를
커널이 회수하려 시도 → NVIDIA UVM 드라이버가 개입해 페이지 마이그레이션/
리매핑 처리**(`UVM GPU1 BH` 커널 스레드가 계속 끼어듦) — 이 처리가 반복되면
ComfyUI 프로세스 스레드는 CPU 99%인데 실제 진행(disk read_bytes, 로그 라인)이
수십 분간 완전히 멈추는 현상이 발생. 이번 스윕에서 GGUF 로드 단계·VAE 디코드
단계 각각에서 최소 2회씩 재현(15분~24분+ 스톨), 매번 `systemctl --user restart
comfyui.service`로만 회복됐고 `/interrupt`는 무효했음.

일반적인 "메모리 부족 → 스왑 스래싱"과 겉보기엔 비슷하지만, **GPU-매핑
메모리가 스왑 압박 받을 때 특유의 오버헤드**(CUDA managed-memory
oversubscription 문서에 기재된 알려진 함정)라는 점에서 원인이 다름. 4.4
오케스트레이터가 목표해야 할 건 "메모리 부족 감내"가 아니라 **GPU-매핑
페이지가 애초에 회수 후보로 잡히지 않을 만큼의 여유 메모리 유지**.

## 참고 — Wan2.2-TI2V-5B 대비 스텝당 속도

`journalctl --user -u wan.service`(2026-07-02~07-05 기록, `video_generator/
hunyuan_server`)에서 LTX와 동일 프레임수(121) 조건 실측 2건 발견:

| 실행 | 해상도 | 프레임 | steps | 총시간 | 스텝당 |
|---|---|---|---|---|---|
| 2026-07-04 11:48 | 1280×704 | 121 | 20 | 1861.6초 | 93.08초/step |
| 2026-07-05 13:32 | 1280×704 | 121 | 20 | 913.5초 | 45.68초/step |
| (참고) 2026-07-05 12:54 | 832×480 | 57 | 20 | 88.0~88.2초 | 4.4초/step |

LTX-2.3-22B baseline(3.3): 1024×576, 121프레임, 8-step, **27.6초/step**.

파라미터는 Wan(5B)이 LTX(22B)보다 훨씬 작지만, 동일 프레임수(121) 조건에서
스텝당 시간은 Wan이 오히려 1.7~3.4배 느림(45.7~93.1초 vs 27.6초) — 해상도
차이(1280×704가 1024×576보다 픽셀 약 1.53배 많음)를 감안해도 방향은 그대로.
단, Wan 수치 자체가 두 실행 간 2배 편차가 있어(위 "UVM 스톨" 노이즈와 같은
계열 가능성) 완전히 클린한 비교는 아님. 그래도 3.2의 "Wan Stand-In 폴백
불필요" 판정이 속도 면에서도 방향이 맞았다는 보강 근거는 됨.

## 결론

- **채택**: baseline(8-step, Q6_K, Face-ID strength 1.0) 그대로 유지. 테스트한
  경량화 레버 중 명확한 순이익을 내는 조합 없음.
- **기각**: step 6(twin 아티팩트).
- **보류/미채택**: Face-ID strength 0.75(정합성 데이터 부족), GGUF
  Q5_K_M(정합성 하락, 속도 이득 불확실).
- **재실측 여지**: Q5_K_M·strength 0.75 모두 "이 세션의 UVM 스톨 노이즈" 영향을
  배제 못 함 — 3.6(로딩 스파이크 완화)이나 4.4(OOM 오케스트레이터) 이후 메모리
  여유가 확보된 조건에서 재검증하면 다른 결론이 나올 수 있음.
