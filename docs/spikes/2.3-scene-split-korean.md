# Spike 2.3 — Nemotron-4B 한국어 씬분할 벤치 (GB10)

작성: 2026-07-30 · 관련 Task: Plans.md 2.3 · 상태: cc:완료

## 목표

`video_generator/langgraph/nodes.py::node_split_scenes`가 실제로 사용하는 씬분할
system_prompt/schema를 그대로 재현해, **Nemotron-3-Nano-4B-GGUF**(NVIDIA, 2.2에서
씬분할 후보로 이월)가 한국어 시나리오를 스키마 준수하는 씬 JSON으로 분할하는지
검증한다. 미달시 Llama3.1 폴백.

## 모델 확보

```
ollama pull hf.co/nvidia/NVIDIA-Nemotron-3-Nano-4B-GGUF:Q4_K_M
```

HF `nvidia/NVIDIA-Nemotron-3-Nano-4B-GGUF` repo의 유일한 gguf 파일
(`NVIDIA-Nemotron3-Nano-4B-Q4_K_M.gguf`)을 ollama가 직행 로드. 2.8GB, 로드/추론
정상 — 2.2에서 우려했던 Mamba2-하이브리드 arch 미지원 이슈 없음.

## 방법

실제 프로덕션 system_prompt(nodes.py `node_split_scenes`)를 그대로 사용, PRD S1
시나리오(발사→우주유영→외계행성→귀환, 우주비행사 얼굴 ref 1장)를 한국어 전체
문장으로 입력해 `/api/chat`에 3회 반복 호출. 비교 대상으로 Llama3.1:8b도 동일
프롬프트로 2회 실행.

## 결과 — Nemotron-3-Nano-4B-GGUF (3회)

| 회차 | 씬수 | JSON 파싱 | 한국어 유지 | duration(2~3) | subject_type 정확도 | 이상 |
|------|------|-----------|--------------|----------------|----------------------|------|
| 1 | 4 | ✓ | ✓ | 4/4 | 4/4 human 정확 | 1개 씬 텍스트에 키릴문자 혼입(`гром음`) |
| 2 | 5 | ✓ | ✓ | 5/5 | 5/5 human 정확 | 없음 |
| 3 | 5 | ✓ | ✓ | 5/5 | 3/5 (2개 씬 human→nonhuman 오분류) | subject_type 오분류만, 언어 오염 없음 |

3회 모두 JSON 배열만 반환(잡설 없음), 한국어 원문 보존(중국어/영어 번역 없음),
duration 스키마 100% 준수. 결함은 간헐적: 키릴문자 혼입 1/3, human/nonhuman
오분류(→ image_role 오배선 위험) 1/3.

## 결과 — Llama3.1:8b (비교, 2회)

| 회차 | 씬수 | JSON 파싱 | 한국어 유지 | duration(2~3) | subject_type 정확도 |
|------|------|-----------|--------------|----------------|----------------------|
| 1 | 6 | ✓ | ✓ | 5/6 (1개 1초 위반) | 3/6 human 정확 |
| 2 | 5 | ✓ | ✓ | 5/5 | 0/5 human 정확(전부 none/nonhuman 오분류) |

Llama3.1은 duration 스키마 위반 1건 추가 발생, subject_type 오분류가 Nemotron보다
빈번(2회 모두 과반 오분류, 2회차는 전체 오분류) — 이 시나리오(사람 1명 반복 등장)에서
Face-ID 매칭에 필요한 human 판정을 Nemotron보다 못 함.

## 결론

**Nemotron-3-Nano-4B-GGUF 채택. 폴백 불필요.** 간헐적 결함(키릴 혼입, subject_type
오분류)이 있으나 Llama3.1 대비 동등하거나 우수하고, 두 결함 모두 JSON 구조 자체를
깨지 않아 `parse_json_lenient` 통과 + 폴백(`fallback = 원문 text`) 경로에 안전하게
잡힘. 프로덕션 배선 시 subject_type 오분류 완화를 위해 `call_llm` 재시도 1회
또는 human 판정 근거(ref_images shows)를 프롬프트에 더 명시적으로 반복하는 보강을
6.x 단계에서 고려할 것(이번 스파이크 범위 밖).
