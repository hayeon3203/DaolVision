# Spike 3.1 — LTX distilled + BFS노드 + Face-ID LoRA 설치·호환·라이센스 확인

작성: 2026-07-30 · 관련 Task: Plans.md 3.1 · 상태: cc:완료

## 목표

R3(캐릭터 일관성 I2V) 게이트 착수 전, "LTX distilled + Face-ID LoRA" 조합이
실제로 ComfyUI에서 설치·로드되는지, 라이센스상 문제 없는지 확인.

## 1. 원래 가정이 틀렸음 — 버전 불일치 발견

Plans.md 3.1의 "LTX distilled"는 원래 **LTX-Video 13B**(2025년, Lightricks
구버전)를 가리켰음. 하지만 착수 전 `docs/model-selection.md`(2.4 이후 리서치)
자체에 이미 다음이 기록돼 있었음:

- 커뮤니티 Face-ID LoRA(`Alissonerdx/LTX-Best-Face-ID`, "Best-Face-ID")는
  **LTX-2.3(22B)** 전용으로 학습됨. LTX-Video 13B는 LoRA 카드에서 아예
  언급조차 안 됨(호환 대상 아님).
- "BFS노드"가 Plans.md/PRD.md/Architecture.md 어디에도 정의돼 있지 않았음.

웹 확인(2026-07-30) 결과 **BFS = `alisson-anjos/ComfyUI-BFSNodes`**
(Best-Face-ID LoRA의 공식 컴패니언 커스텀노드). 그리고 사용자 질문("LoRA는
2.3이 최대냐, 더 가벼운 LTX 없냐?")에 대한 답: LTX-2.3는 dev/distilled/fast/pro
4개 체크포인트로 나오는데, distilled가 8-step 경량판. 이 LoRA가 지원하는
범위에서 이보다 가벼운 LTX 계열은 없음 — 단, 공식 리포(`Lightricks/LTX-2.3`)의
distilled 파일은 46.1GB bf16 그대로라 실제로는 "가벼움"이 아니었음. 대신
**커뮤니티 GGUF 양자화**(`unsloth/LTX-2.3-GGUF`의 `ltx-2.3-22b-dev-Q6_K.gguf`,
17.8GB, bf16 대비 약 61% 축소)와 **경량 distill LoRA**(`Kijai/LTX2.3_comfy`의
rank-111 dynamic LoRA, 2.74GB, 공식 384-rank LoRA 7.61GB 대비 약 64% 축소)가
실제 경량 경로 — 그리고 이 조합이 바로 Best-Face-ID LoRA 저자가 공식
`workflows/Best-FaceID_v1.0_Workflow.json`에서 검증해서 배포한 조합임(자체
예시 영상 14개 포함, `examples/sample_1.mp4` 등).

**결론: "LTX distilled" 재정의 필요** — 13B(구버전) 아니라 **LTX-2.3-22B-dev
(GGUF Q6_K) + distill LoRA**로 스택 확정. `docs/model-selection.md` 결정표
갱신 완료.

## 3. 설치 중 발견한 부작용 2건 — 즉시 원복

1. **numpy 2.x 승격**: `librosa`/`albumentations` 설치가 numpy를 1.26.4→2.4.6로
   올림 → `mediapipe`(`Stand-In_Preprocessor_ComfyUI` 등 기존 Wan 파이프라인이
   씀, `numpy<2` 요구)가 깨질 뻔함. `numpy<2,>=1.26`로 즉시 되돌림, 이후
   mediapipe/librosa/insightface 전부 정상 확인.
2. **opencv-contrib-python 섀도잉**: `librosa`/KJNodes 요구사항의
   `opencv-python-headless`가 같은 `cv2` 네임스페이스를 덮어써서 기존
   `opencv-contrib-python`(4.11.0, `cv2.face` 등 contrib 전용 모듈 포함)이
   비활성화될 뻔함(`cv2.__version__`이 5.0.0으로 바뀜, contrib 모듈 접근 불가).
   `opencv-python`/`opencv-python-headless` 제거 후 `opencv-contrib-python`
   `--force-reinstall`로 복구, `cv2.face` import 확인.

두 건 모두 **기존 프로덕션 Wan/Stand-In 파이프라인에 영향 없이** 복구 완료.

## 4. 워크플로 로드 검증 (ComfyUI 재기동 + API 확인)

브라우저 없이 헤드리스로 검증 가능한 두 축:

1. **노드 타입 전체 해석**: 워크플로 39종 노드 타입(유틸리티 Reroute/Get·SetNode
   제외) 전부 `/object_info`에 등록됨 확인. 단, 설치된 GGUF 노드가
   community 표준 `UnetLoaderGGUF`가 아니라 이 ComfyUI 자체 내장
   `LoaderGGUF`(동일 시그니처, `gguf_name` 단일 위젯)로 이름이 달라
   워크플로 JSON에서 타입명 교체함.
2. **모델 파일 드롭다운 전체 해석**: 로더 노드 9개의 파일 위젯 값 전부
   `/object_info`의 실제 드롭다운 옵션에 존재 확인. 단, distill LoRA
   위젯값에 원저작자 개인 폴더 구조(`ltx-2/2.3/...`) 접두어가 남아있어
   우리 설치 위치(평평한 `models/loras/`)와 안 맞음 → 접두어 제거해 파일명만
   남김.

수정 후 **39개 노드 타입 + 9개 모델 파일 참조 전부 FOUND** — 실제 생성 실행
(3.2에서 진행 예정)까지는 아니지만, "그래프가 ComfyUI에서 로드된다"는 DoD는
충족.

## 결론

- **호환 조합 확정**: LTX-2.3-22B-dev(GGUF Q6_K) + distill LoRA(rank-111) +
  Best-Face-ID LoRA + BFS Nodes. 원래 Plans.md가 가정한 "LTX-Video 13B
  distilled"는 폐기.
- **설치·로드 검증 완료**(헤드리스 API 기준). 실제 생성 품질(참조얼굴 유지)은
  3.2에서 검증.
- **라이센스 이슈 없음**(개인/소규모 사용 기준, $10M+ 매출 법인 조건은
  해당 없음).
- **재현성 참고**: numpy/opencv 버전 충돌은 3.2 이후 다른 커스텀노드
  설치 시에도 재발 가능 — pip install 전 `numpy`/`opencv-contrib-python`
  버전 고정 확인 습관화 필요.
