# Spike 3.3 — LTX I2V 파이프라인 병목 프로파일링

작성: 2026-07-30 · 관련 Task: Plans.md 3.3 · 상태: cc:완료

## 목표

3.2에서 확정된 LTX-2.3-22B Face-ID I2V 워크플로(`ltx_faceid.json`)의 구간별
(모델로드/샘플링/디코드) 소요시간을 실측 — 3.4(경량화 스윕)·3.5(attention
backend)의 baseline 숫자로 쓴다.

## 방법

`ltx_faceid.json`은 KJNodes SetNode/GetNode(프론트엔드 전용 pseudo-node,
`/object_info`에 없음 확인)로 배선돼 `/prompt` API에 직접 못 보냄(3.2와 동일
제약). 브라우저 없이는 `window.app.graphToPrompt()`를 호출할 수 없어, 이번
스파이크 전용으로 격리 venv(`/home/admin/comfyui-bench-venv`, 프로덕션
ComfyUI venv `/home/admin/.venv`와 분리 — 3.1의 numpy/opencv 오염 전례 반복
방지)에 Playwright를 설치해 헤드리스 브라우저로 변환·제출하는 스크립트
(`video_generator/langgraph/tests/probe_ltx_profile.py`)를 작성했다.

설정은 3.2 STATE.md가 확정한 기본값을 그대로 재현(파라미터 변경 없이 baseline만
측정 — 변경 실험은 3.4 몫):
- 해상도 1024×576(16:9), 5초/24fps(121프레임), distill LoRA weight 0.6,
  Face-ID LoRA strength 1.0, 8-step
- 3.2가 쓴 원본 참조 얼굴 사진·오디오 파일이 ComfyUI input 디렉터리에서 소실돼
  있어(`pasted/image (721).png`, mp3 파일 모두 없음), 타이밍 목적상 얼굴/오디오
  내용은 무관하므로 기존에 남아있던 대체 이미지(`face_ref.png`)로 교체 제출.

타이밍은 ComfyUI 자체 로그(`ComfyUI/user/comfyui.log`)의 타임스탬프 라인
(`got prompt` / `Requested to load` / `loaded completely` / 샘플러 tqdm
진행바 / `Prompt executed in N seconds`)에서 직접 추출. 웹소켓 실행 이벤트
캡처도 같이 시도했으나(첫 실행은 recv 타임아웃으로 유실, 재접속 워처는 완료
직전에야 붙어 4개 이벤트만 잡음) 서버 로그가 더 신뢰도 높은 소스라 최종
분석은 로그 기준으로 함.

## 1차 시도 — 실패(측정 불가), 중요 부수 발견

최초 제출(prompt_id `a608...`, 07:31:49 제출) 도중 사용자가 별도로
`flux_server.py`(huyuan-env, T2I 서버)를 기동하면서 GPU 30~50GB를 추가로
점유 — ComfyUI의 GGUF dequant 스레드(단일 스레드, 99.9% CPU)가 **24분+ 동안
disk read 1MB 미만**으로 사실상 정지(스왑 스래싱). 시스템 메모리 free
1.7Gi/스왑 free 630Mi까지 내려가 earlyoom SIGKILL 문턱(5%) 근처까지 감. 사용자
확인 후 `flux_server.py` kill -9로 해소, `/interrupt`·큐 clear가 노드 내부
C-level 루프엔 안 먹혀서 `systemctl --user restart comfyui.service`로 재기동 후
깨끗하게 재측정.

**이 자체가 4.4(OOM 오케스트레이터)에 중요한 실측 근거**: GB10 통합메모리에서
서로 다른 서비스(ComfyUI GGUF 로드 vs 별도 T2I 프로세스)가 동시에 대형 모델을
로드하면 단순히 "느려지는" 게 아니라 **스왑 스래싱으로 사실상 정지**한다 —
동일 작업이 정상 조건 92초 vs 경합 조건 24분+(40배 이상). 2.4 스파이크의
"전 모델 상주 기각" 결론과 같은 방향의 근거 하나 추가.

## 2차 시도 — 클린 측정 (prompt_id `6425...`, ComfyUI 재기동 직후 제출)

**총 소요: 523.44초 (8분43초)**, `Prompt executed in 523.44 seconds` 로그로 확정.

| 구간 | 시각 범위 | 소요 | 비중 | 내용 |
|---|---|---|---|---|
| 모델 로드 | 08:18:02.627 → 08:21:12.538 | **189.9초 (3분10초)** | 36.3% | 텍스트인코더(Gemma, 14.8GB) 로드 86.3초 + VideoVAE 로드 + GGUF UNet(17.2GB, Q6_K dequant 포함) 로드 91.8초 |
| 샘플링(8-step) | 08:21:12.538 → 08:25:05.465 | **232.9초 (3분53초)** | 44.5% | tqdm 실측 27.61s/it, 스텝당 평균 ~29.1초 |
| 디코드+후처리 | 08:25:05.465 → 08:26:46.074 | **100.6초 (1분41초)** | 19.2% | AudioVAE 디코드 2.5초, VideoVAE 재로드/디코드, **텍스트인코더(14.8GB) 재로드 26.4초 — 원인 불명, 회피 가능해 보이는 오버헤드** |

## 결론 / 3.4·3.5로 넘길 시사점

1. **샘플링이 최대 단일 병목(44.5%, 233초)** — step 수(현재 8, task 3.4가
   실험할 값)와 스텝당 시간(attention backend, task 3.5가 다룰 영역)이 가장
   직접적인 레버. 스텝당 ~29초는 SageAttention3(GB10/Blackwell 전용, 3.5
   대상) 적용 시 얼마나 줄어드는지가 3.5의 핵심 측정값이 돼야 함.
2. **모델 로드도 무시 못할 비중(36.3%, 190초)** — 이 중 GGUF dequant는 정상
   조건에서 92초로 과도하지 않음(1차 시도의 24분+는 동시 경합이 원인이지
   dequant 자체 결함 아님). Q6_K→Q5_K_M(3.4 대상)이 이 구간을 얼마나
   줄이는지 확인 필요.
3. **디코드 후처리 구간의 텍스트인코더 재로드(26.4초, 전체의 5%)는 불필요해
   보이는 낭비** — 어떤 노드가 이 시점에 텍스트인코더를 다시 요청하는지
   원인 규명 후 제거하면 공짜로 5% 단축 가능. 3.6(로딩 스파이크 완화) 조사
   대상에 추가할 것.
4. **동시 상주 서비스 경합은 속도저하가 아니라 사실상 정지를 유발한다** —
   4.4 오케스트레이터 설계 시 "느려짐 감내" 전제가 아니라 "완전 정지 방지"를
   목표로 잡아야 함(GB10 통합메모리 특성상 스왑 스래싱이 CPU 바운드 작업까지
   마비시킴, GPU 전용 메모리 분리 아키텍처와 다른 실패 모드).
