### 핵심 메시지

**2026-07-03 완성, 현재 실서버 운영 중** (:8700 포트, Open WebUI 연동)

#### 작동 흐름
1. 시나리오 입력
2. 자동 씬분할
3. 클립 자동 생성
4. **👤 사람이 3단계에서 승인·재생성 선택** (핵심 차이)
5. 자동 편집
6. 최종 영상 완성

#### 주요 특징
- **사람 개입**: 여러 시간 경과 후에도 승인 재개 가능 → 언제든지 돌아와서 "이 클립 다시 만들어"
- **품질 튜닝 완료** (2026-07-04): 모션 자연스러움, 인물 일관성, 무한 로딩 버그 모두 해결
- **믿을 수 있음**: 시스템 재시작 후에도 정확히 멈춘 지점에서 재개

### 왜 이전과 다른가?

| 구분 | 구 Hunyuan 모델 | 현재 LangGraph |
|------|----------------|----------------|
| **에이전트** | OpenShell (일꾼만 있음) | LangGraph (일꾼 + 매니저) |
| **사람 승인** | 불가능 (순차만 가능) | **가능** (멈춤·승인·재개) |
| **상태 기억** | 각자 따로 | 중앙에서 모두 기록 |
| **운영 가능 여부** | 단순 실험용 | **실제 서비스 가능** |

**핵심**: OpenShell은 "이야, 일하는 사람"이지만 LangGraph는 "일하는 사람 + 그들을 관리하고 상태를 기억하는 매니저" → 사람의 "잠깐, 이거 다시 만들어" 요청을 처리 가능

**외부 시스템 연동**

- UI: Open WebUI에 Function 임베드 (마크다운 + 클립 링크 + 상태 마커)

## 🔄 기술 결정: OpenShell → LangGraph

### 기술 비교

| 기준 | OpenShell 인스턴스 N개 | LangGraph (현재 선택) |
|------|----------------------|----------------------|
| **사람 승인 흐름** | 구현 불가 (순차만 가능) | ✅ `interrupt()` 3곳 native support |
| **상태 재개** | 직접 구현 필요 (DB + 복원 로직) | ✅ checkpoint로 정확한 지점부터 |
| **메타데이터 공유** | "이 씬의 원본 프롬프트는?" → DB 쿼리 | ✅ state dict에 모두 포함 |
| **2시간 뒤 재개** | "어느 OpenShell이 어느 상태?" 추적 필요 | ✅ `thread_id`로 checkpoint 로드 |
| **병렬 안전성** | 동기화 버그 위험 | ✅ 그래프가 순서 보장 |
| **필요 코드량** | ~500+ 줄 (상태머신 직접 구현) | ✅ 이미 제공됨 |

### 왜 LangGraph인가?

**간단 설명 (비유)**
- **OpenShell**: 배달원 여러 명이 각자 독립적으로 일함 → "2번 주소는 누가 가지?" 혼란
- **LangGraph**: 배달원들 + **매니저가 전체 배달 진행을 한곳에서 기록** → "누구나 현재 상태를 알 수 있음"

**기술 설명**
- 영상 제작은 **사람이 중간에 "이거 다시 만들어" 요청**하는 워크플로우
- 순차만 되는 OpenShell로는 이 요청을 처리할 수 없음
- LangGraph의 그래프 구조 + checkpoint가 이 개념을 native로 지원
- 결국 OpenShell도 가능하지만, "상태를 누가 기억할 건가" 문제를 직접 풀어야 하므로 → **건축학적으로 나쁜 선택**
